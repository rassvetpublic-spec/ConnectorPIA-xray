# Коннектор: план доработок и решения

Передача другому аккаунту для реализации. Дата: 12.09.2026.
Этот документ — план. В рамках его подготовки код и настройки подключения не изменялись.

## 1. Задача и приоритеты пользователя

Одна кнопка подключает Happ → PIA. Панель достоверно показывает фактическую цепочку, доступность сервисов, географию выхода, задержки и трафик. Коннектор управляет PIA и постепенно получает полное поддерживаемое управление Happ.

Выбор маршрута: доступность нужных сервисов → устойчивость → задержка; важность upload/download меняется по текущей нагрузке. Стабильный маршрут предпочтительнее быстрого, который постоянно обрывается. При активной отдаче учитывать upload, при интерактивной работе — задержку и jitter. Не переключаться из-за единичного плохого измерения.

## 3. Подтверждённые проблемы текущего кода

- `vpn_monitor.py` заполняет `network.region` через `piactl get region`. Одного выбранного региона недостаточно, чтобы доказать фактический сервер текущего соединения.
- Интервалы сейчас: TCP — 3 секунды, HTTP — 10 секунд. Цели HTTP: только ChatGPT и Gemini.
- Заголовки таблиц Tkinter не имеют обработчиков сортировки. Строки проверок удаляются и создаются при каждом обновлении.
- `poll_status()` выполняет получение сетевых счётчиков синхронно в потоке интерфейса; ошибки проглатываются. Возможно зависание панели и отображение старого состояния без явной ошибки.
- В README управление Happ отмечено как ещё не реализованное. Не считать обнаруженные настройки готовым управляющим API.

Остальные пункты ниже — решения и проверки для разработчика, а не заявления о уже реализованном поведении.

## 4. P0 — достоверное состояние PIA и маршрута

### Решение

Разделить данные на отдельные поля:

- `requested_region`: что выбрано пользователем или автоматикой;
- `connected_region`: регион установленного соединения, только если подтверждён;
- `transport_endpoint`: фактический удалённый адрес OpenVPN и порт;
- `tunnel_local_ip`: адрес внутри туннеля;
- `public_exit_ip`, `exit_country`, `exit_city`: внешний выход и отдельно результат геопроверки;
- `observed_at`, `source`, `confidence`: давность, источник и степень подтверждения.

Исследовать ограниченный набор полей `piactl -u dump daemon-state` и события `piactl -u watch`; не печатать полный дамп. Сверить смысл полей с исходниками соответствующей версии. Не назначать `bestLocation`, `nextLocation` или `chosenLocation` активным сервером по одному названию поля.

Активный endpoint подтверждать данными установленного соединения и актуальными журналами/состоянием. `data/pia.ovpn` использовать как вспомогательный источник: файл может относиться к предыдущей попытке. Через локальный SOCKS сокет OpenVPN видит `127.0.0.1:10808`, поэтому обычный список TCP-соединений OpenVPN не раскрывает удалённый PIA endpoint.

Сделать адаптер версий PIA: штатные команды для базового управления, нестабильный интерфейс — после проверки возможностей. Не расширять бесконечно ручную таблицу из четырёх соответствий имён регионов: построить и проверять модель идентификаторов из доступных списков клиента.

Получать изменения событийно, с контрольным опросом каждые 5–10 секунд. Ручное переключение в оригинальном PIA должно обнаруживаться без участия Коннектора.

Ввести `connection_generation`: увеличивать при переподключении, смене endpoint или подтверждённой смене цепочки. Каждый замер получает поколение при старте. Поздний ответ старого поколения не попадает в качество нового маршрута. Гео и скорость также привязать к поколению; старые значения показывать только с отметкой «предыдущее соединение».

### Приёмка

1. Переключить PIA вручную: панель показывает переход, затем подтверждённое соединение не позже 10 секунд после появления данных у службы.
2. Проверить выбор региона без переподключения, Auto, переподключение внутри одного региона и неудачное подключение.
3. При отсутствии подтверждения писать «активный сервер не подтверждён», не выдавать выбранный за активный.
4. Остановка монитора даёт явную отметку «данные устарели»; ошибки чтения видны в диагностике.
5. Ответы старого соединения не меняют показатели нового.

## 5. P0 — редкие и корректные HTTP-проверки

### Интервалы по умолчанию

| Проверка | Период | Условия |
|---|---:|---|
| Состояние локальных процессов/SOCKS | 3 с | Не обращается к внешним сайтам |
| TCP до выбранных внешних целей | 15 с | Не более трёх целей; не создавать параллельный дубль |
| ChatGPT и Gemini HTTP | 180 с на сайт | Случайное отклонение ±20%, разнести по времени |
| Дополнительные HTTP-цели | 300 с на сайт | Проверять по очереди |
| Внешний IP/гео | 600 с | После смены соединения один запрос через 15–30 с |
| Полный тест скорости | Вручную | Автоматический — отдельно включаемый, с лимитом трафика |

Ранее пользователь просил ping каждые 3 секунды. Сохранить настраиваемый режим частых TCP-замеров выбранной цели, но не распространять его на HTTP и массовую проверку всех серверов. Объяснить в интерфейсе, что TCP-время не является ICMP ping.

Эти интервалы снижают нагрузку, но не гарантируют отсутствие ограничений сайта.

### Расширение списка

Реестр целей с полями: URL, категория, включено, период, таймаут, максимальный ответ, ожидаемый тип ответа, классификатор, значимость для восстановления.

Начальный набор: ChatGPT, Gemini, Wikipedia, GitHub, YouTube. Первые два — приоритетные для пользователя; дополнительные сайты нужны для сравнения, а не как доказательство доступности ИИ. Перед включением подтвердить конечные URL, редиректы и пригодность публичной страницы для редкой проверки. Не включать все цели автоматически в условие «интернет сломан».

Добавить пользовательские цели, кнопку «проверить сейчас», время следующей проверки, HTTP-код и причину результата. Ручная кнопка тоже соблюдает действующий запрет повторных запросов.

### Обработка ответов

- `200` с HTML означает «страница доступна», а не «чат готов в вашем аккаунте».
- Отдельные состояния: доступна, запрет страны, требуется вход, CAPTCHA/защита, ограничение частоты, ошибка сети, ошибка сервиса, неизвестно.
- `403` сам по себе не является запретом страны. Для геоблокировки нужен конкретный признак в видимом ответе/структурированной ошибке.
- При `429` учитывать `Retry-After` в секундах и формате даты. Без него: паузы 15 → 30 → 60 минут, ограниченные сверху; положительный jitter добавлять после минимальной паузы.
- CAPTCHA и `429` не запускают смену IP/серверов. Не пытаться автоматически обходить защиту сайта.
- Для `5xx` применять паузу и сравнивать независимые цели, а не немедленно менять маршрут.
- Кэшировать результаты; ограничивать размер ответа, время запроса и число редиректов. HEAD использовать только там, где он даёт нужный результат; для определения геозапрета часто требуется GET.
- Планировщик использует монотонное время; не догоняет пропущенные проверки пачкой после сна Windows.
- Проверки должны идти по тестируемой цепочке. Отдельно проверять поведение DNS: привязка исходящего IP не доказывает маршрут DNS-запроса.

Приёмка: тесты ответов 200/403/429/5xx, Retry-After, CAPTCHA, геозапрета и таймаута на локальных фикстурах; проверка интервалов виртуальными часами. Не нагружать реальные сайты ради тестов.

## 6. P1 — сортировка колонок и удобство панели

Реализовать в Tkinter и HTML-панели одинаковую модель сортировки.

- Нажатие заголовка: возрастание/убывание, стрелка направления.
- Числа сортируются численно: 9 мс перед 100 мс; единицы измерения добавляются при отображении.
- Неизвестные значения всегда внизу; одинаковые значения имеют стабильный порядок.
- Для статусов задать явный порядок; для приложений — сортировку по имени, пути и режиму.
- Обновлять строки по устойчивому ID, сохраняя сортировку, выбранную строку и положение прокрутки.
- Сохранять настройки пользователя между запусками; в HTML — не терять их при обновлении страницы.
- Разделить составную колонку качества на успех %, median, p95, jitter, число измерений и возраст данных, если эти показатели доступны.
- Сетевые обращения и получение счётчиков перенести из потока интерфейса в worker; публиковать готовый снимок.

Приёмка: смешанные числа/пропуски/статусы, обновление каждые несколько секунд, сохранение выбора, отсутствие зависания при задержке службы на 5 секунд.

## 7. P1 — Happ: активный сервер и его задержка

### Источники данных

Исследовать `HKCU\Software\Happ\OrganizationDefaults\Preferences`: обнаруженные `lastServerName`, `lastServerHost`, `lastServerPort`, `lastServerGuid` трактовать как последнюю выбранную запись, пока активность не подтверждена.

Сопоставлять её с состоянием Happ, процессом сетевого ядра и его установленными соединениями. Одно наличие процесса не означает подключение; один сокет не всегда однозначно указывает выбранный сервер. Отдельно учитывать тестовые соединения и обновление подписок. При недостаточных правах/неоднозначности показывать ограниченность данных.

Панель: название, хост:порт, протокол/транспорт, выбран/подключён/не подтверждён, время соединения, источник данных, последнее измерение.

### Три разных измерения

1. До входного Happ endpoint — TCP connect по прямому пути, соответствующему обходу PIA.
2. Через Happ — запрос к контрольной цели через локальный SOCKS.
3. Через всю цепочку Happ → PIA — прикладная проверка через туннель PIA.

Не объединять эти цифры под одним «ping». Встроенный тест Happ использовать только после выяснения, что именно он измеряет. Для `happ-tcping.exe` сначала установить поддерживаемый контракт запуска и формат результата; не выдумывать аргументы.

Кнопки: «Проверить активный», «Проверить выбранные», «Остановить тест». Массовый тест ограничить по параллелизму, повторениям и частоте. Его трафик не должен ухудшать активную цепочку.

Приёмка: ручное переключение Happ отражается в панели, тестовые соединения не становятся активным сервером, недоступный endpoint даёт ошибку с давностью, а не старый зелёный результат.

## 8. P2 — Happ: подключение и смена сервера

Сначала составить матрицу возможностей установленной версии: получить список, прочитать активный, подключить конкретный ID, отключить, запустить тест, читать/менять настройки.

Предпочтение: документированный API/IPC/CLI → подтверждённые URI-команды → адаптер управления интерфейсом, если программного управления нет. Последний явно обозначить как зависящий от версии и языка интерфейса. Наличие команды `happ://connect` не доказывает возможность выбрать конкретный сервер через URI.

`%LOCALAPPDATA%\Happ\subs.db` содержит непрозрачные данные: не редактировать бинарный снимок наугад. Для списка профилей использовать поддерживаемый экспорт/интерфейс. Секретные профили не помещать в общий status JSON или HTML.

Транзакция переключения:

1. Захватить общий управляющий lock, остановить автоматическое восстановление, запомнить рабочую пару.
2. Проверить кандидата настолько, насколько возможно без разрыва текущей цепочки.
3. Безопасно перевести PIA в переходное состояние с сохранением выбранной политики защиты трафика.
4. Переключить Happ, дождаться подтверждённого endpoint и SOCKS.
5. Подключить PIA, подтвердить новое поколение соединения и контрольную доступность.
6. При ошибке вернуть предыдущую пару; при неудаче отката показать ошибку и остановить цикл переключений.

Не объявлять успешным запуск процесса или отправку команды. Успех — подтверждённое соединение и проверка трафика. Не обещать бесшовность: активные TCP-сессии могут прерваться.

## 9. P2 — все параметры Happ: инвентаризация и безопасное применение

Сделать реестр параметров со столбцами: название в UI, внутренний ключ, тип, допустимые значения, источник, секретность, чтение поддержано, запись поддержана, требуется перезапуск, способ проверки, способ отката.

Покрыть группы: SOCKS/HTTP inbounds и авторизация; системный прокси; TUN и его провайдер; DNS/FakeDNS; маршрутизация и исключения; IPv4/IPv6; фрагментация; multiplexing; параметры транспорта доступного профиля; подписки и обновление; запуск/окно; журналирование. Наличие каждой группы и её точные значения проверять в установленной версии, не считать перечень доказательством поддержки.

Обнаруженные места: реестр Happ, `%LOCALAPPDATA%\Happ\config.json`, `routing.json`, `subs.db`. Различать настройки пользователя, сгенерированные файлы и кэш. Нельзя считать любой `config.json` активным конфигом Xray: он может относиться к TUN/sing-box.

Применение: прочитать → построить понятный diff → резервная копия → применить поддерживаемым способом → при необходимости перезапустить → прочитать обратно → проверить соединение → при ошибке откатить. Не редактировать живой реестр в надежде, что Happ перечитает его: приложение может перезаписать изменения из памяти.

Неизвестные поля сохранять без изменения. Неподдерживаемые параметры показывать как недоступные с причиной. «Все параметры» считается выполненным только при наличии матрицы покрытия всех пользовательских настроек установленной версии и явного списка исключений.

## 10. P2 — надёжные настройки обхода PIA

Сохранить работающий подход через службу, а не прямую запись `data/settings.json`. Проверять совместимость нестабильного `piactl -u applysettings` после обновления PIA.

Добавить поиск, сортировку, несколько выбранных приложений, импорт/экспорт без секретов, diff и откат. Сохранять неизвестные значения DNS/MTU и полей правил, которые пользователь не менял.

Защищать обход реального сетевого ядра Happ (`core\xray.exe` в обнаруженной установке), а не только Happ.exe: проверить путь и текущий процесс. Иначе возможен захват внешнего транспорта Happ туннелем PIA. Не менять правило «все прочие приложения» без явного действия пользователя.

Один общий межпроцессный lock для запуска, настройки, переключения и восстановления. Файл maintenance с таймаутом сам по себе не исключает гонку уже запущенных операций.

Приёмка: внешнее изменение правил обнаружено; правка одного поля не меняет другие; сбой сохраняет рабочую конфигурацию; правила проверены реальным маршрутом тестового процесса, а не только чтением настроек.

## 11. P3 — динамический выбор пары Happ/PIA

Хранить историю в SQLite по паре профилей и фактическим endpoint, с отдельными сессиями. Окна 5/30/120 минут: доступность, обрывы, время восстановления, median/p95/jitter, возраст и объём выборки, отдельные оценки upload/download.

Сначала исключать маршруты с подтверждённой недоступностью нужных сервисов и частыми обрывами. Затем сравнивать задержку и, с учётом нагрузки, скорость. Не сводить всё к одному среднему ping.

Нагрузку сглаживать за 30–60 секунд. Высокий текущий upload сам по себе не доказывает узкое место: учитывать рост задержки под нагрузкой и свежую оценку пропускной способности. Старые измерения другой пары не использовать как текущую ёмкость канала.

Стартовая политика для калибровки: минимальное пребывание 10 минут, улучшение не менее 20% по актуальному критерию с достаточной выборкой, штраф за обрывы, ограничение переключений в час. Аварийное восстановление обходит минимальное пребывание, но сохраняет лимит повторов. При активной передаче откладывать необязательное переключение.

Fallback выбирать по месту отказа: Happ endpoint недоступен → восстанавливать Happ; Happ работает, PIA не устанавливает туннель → восстанавливать/менять PIA; один сайт отвечает защитой/429 → пауза только этому сайту. Не менять оба узла одновременно без необходимости — иначе теряется причина отказа.

Режим «только Happ» — отдельная опция пользователя с явным изменением политики маршрутизации. Не переходить молча на прямой интернет.

## 12. Геотест и будущий отказ от оболочек

Геопанель показывает отдельно IP выхода, страну/город по источнику геоданных, заявленную локацию сервера и время проверки. Несовпадение этих полей допустимо и не исправляется подстановкой страны из названия профиля.

Сохранить пользовательский геотест 2IP. Проверить актуальный адрес и условия API перед реализацией автоматического гео; если нужен токен, хранить вне статуса/логов. Без API показывать внешний IP и ссылку на ручную проверку, не изображать автоматическое подтверждение страны.

Для дальнейшего самостоятельного приложения сначала выделить интерфейсы HappAdapter, PiaAdapter, ProbeScheduler, ConnectionController и хранилище состояния. Интерфейсы не должны зависеть от Tkinter или HTML.

Затем отдельный этап: собственное управление процессами Xray/OpenVPN, импорт профилей, DNS, маршрутизация, правила приложений Windows, восстановление после сна/смены сети, защита от утечек согласно настройкам пользователя. Это отдельный проект по сложности; удалять штатные приложения только после функционального сравнения и проверенного отката. Существующие протоколы и криптографию использовать из поддерживаемых ядер.

## 13. Порядок реализации и передача результата

1. Зафиксировать исходное состояние и прогнать имеющиеся тесты.
2. Исправить состояние PIA, поколения соединений, устаревание данных и поток интерфейса.
3. Внедрить редкий планировщик HTTP, классификаторы и расширяемые цели.
4. Добавить сортировку обеих панелей.
5. Реализовать подтверждённое состояние Happ и отдельные виды замеров.
6. Закрыть управление Happ: сначала матрица возможностей, затем переключение и параметры.
7. Укрепить транзакции настроек и правила PIA.
8. После накопления достоверных измерений включать динамический выбор маршрута.

Для каждого этапа передать: изменённые файлы, результаты тестов, ручные проверки, ограничения, резервную копию и способ отката. Не считать тест «команда принята» достаточным доказательством работы подключения.

Обязательные сценарии итоговой проверки: ручная смена PIA/Happ, сон Windows, потеря сети, смена адаптера, неверный профиль, остановка службы, ограничение сайта, одновременно нажатые кнопки, рестарт монитора, возврат прежней пары после неудачного переключения. Сетевые сценарии запускать контролируемо, учитывая разрыв текущей пользовательской связи.
