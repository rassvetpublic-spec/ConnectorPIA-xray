# GitHub Workflow ConnectorPIA-xray

Практическая памятка по рабочему процессу репозитория. Обязательные правила AI-исполнителей находятся в корневом `AGENTS.md`.

## Рабочий цикл

`Issue → Scope → FAST-CLAIM → fresh branch → Draft PR → CI/Evidence → Ready for review → независимый QA при необходимости → mtd → merge → проверка main`

## Канонические сущности

- **Issue** — задача: цель, Scope, Out of scope, зависимости и критерии готовности.
- **Branch** — изолированное рабочее изменение от свежего `main`.
- **Pull Request** — проверяемый ChangeSet.
- **Actions / CI** — автоматические Evidence.
- **Review / QA** — проверка результата и рисков.
- **Project** — визуальное представление Issues/PR, но не новый источник требований.
- **Release** — официально выпущенная версия.

## Статусы Project

Рекомендуемые значения поля `Статус`:

- `Входящие`;
- `Нужно разобрать`;
- `Готово к работе`;
- `В работе`;
- `Проверка QA`;
- `Заблокировано`;
- `Готово`.

Поле `Исполнение`:

- `Свободно`;
- `В очереди`;
- `Активно`;
- `На проверке`;
- `Заблокировано`;
- `Освобождено`.

## Приоритет

- `P0` — критично: безопасность, потеря данных или блокер ключевого этапа;
- `P1` — важно;
- `P2` — полезно;
- `P3` — позже.

Приоритет не отменяет зависимости и блокировки.

## Восемь представлений Project

Контракт находится в `config/project_views.json`:

1. `00 — Dashboard`;
2. `01 — Queue`;
3. `02 — Active Work`;
4. `03 — QA Gate`;
5. `04 — Release Flow`;
6. `05 — Roadmap`;
7. `06 — Blocked / Parking`;
8. `07 — Agent KPI`.

Если административный API недоступен, наличие этого файла не считается доказательством, что Project уже создан или настроен. Фактическая настройка должна подтверждаться отдельным Evidence.

## PR и QA

PR связывается с Issue. Каждый критерий готовности трассируется до файла/модуля и проверки. Для значимых изменений QA должен проверять точный HEAD независимо от Implementation Worker.

После изменения HEAD прежний QA считается устаревшим, пока Controller не докажет обратное через Impact Assessment.

## Финальный Gate

Merge возможен только после явной команды владельца `mtd`, `MTD` или `мтд`.

CI PASS, review approval и QA PASS означают только готовность к возможному принятию.

## Если что-то сломалось

Зафиксировать четыре вещи:

1. что именно не прошло;
2. на какой revision;
3. где Evidence;
4. что нужно изменить для воспроизводимого PASS.

Красный CI и ограничения платформы не скрываются и не переименовываются в PASS.
