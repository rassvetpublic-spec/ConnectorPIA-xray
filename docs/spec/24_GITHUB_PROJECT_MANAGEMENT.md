# GitHub — ведение проекта и совместная разработка ConnectorPIA-xray

Этот документ задаёт каноническую политику GitHub-процесса проекта.

## 1. Разделение источников истины

- `docs/` — принятая архитектура, спецификации и правила;
- Issues — фактическое состояние работ, Scope, зависимости, блокеры и критерии готовности;
- Pull Requests — ChangeSet;
- Actions / tests / review — Evidence;
- Releases — официальные выпуски;
- GitHub Project — производная проекция Issues/PR.

Project не может содержать уникальные требования, отсутствующие в Issue или канонической документации.

## 2. Единица работы

По умолчанию одна самостоятельная работа оформляется как:

`Issue → рабочая ветка → PR → Evidence → QA → mtd → merge`.

Несвязанные задачи не смешиваются в один PR.

## 3. Scope

Каждая рабочая Issue должна явно содержать:

- цель;
- Scope;
- Out of scope;
- зависимости;
- способ проверки;
- критерии готовности.

Расширение Scope без фиксации запрещено.

## 4. Project

Канонический машинный контракт представлений: `config/project_views.json`.

Project должен иметь восемь рабочих представлений:

1. `00 — Dashboard`;
2. `01 — Queue`;
3. `02 — Active Work`;
4. `03 — QA Gate`;
5. `04 — Release Flow`;
6. `05 — Roadmap`;
7. `06 — Blocked / Parking`;
8. `07 — Agent KPI`.

Канонические пользовательские поля:

`Статус`, `Этап`, `Приоритет`, `Тип`, `Область`, `Размер`, `Итерация`, `Исполнитель`, `Проверяющий`, `Исполнение`, `Цель`, `Риск`, `Доказательство`.

Фактическое существование Project, полей и представлений подтверждается платформенным Evidence. Наличие JSON-контракта само по себе не считается настройкой GitHub Project.

## 5. QA и Evidence

Критерий считается выполненным только при наличии проверяемого Evidence. Независимый QA работает по `QA_PROTOCOL.md` и проверяет точную revision.

Изменение HEAD после QA требует Impact Assessment и, при необходимости, DELTA/FULL QA.

## 6. Main и merge

Обычная работа напрямую в `main` запрещена процессом.

Финальный ручной Gate владельца безусловен:

> Merge выполняется только после явной команды `mtd`, `MTD` или `мтд`.

CI PASS, approved review и QA PASS не заменяют `mtd`.

## 7. Административный provisioning

Ruleset/branch protection, GitHub Project v2, labels и другие платформенные объекты должны считаться `PROVISIONAL`, пока их фактическое состояние не подтверждено через GitHub API/UI Evidence.

Если текущий коннектор не предоставляет mutation для такой настройки, исполнитель обязан зафиксировать ограничение, а не заявлять ложный PASS.
